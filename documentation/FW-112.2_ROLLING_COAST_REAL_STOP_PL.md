**FW-112.2 (ta karta):** postój = `real_stop` ORAZ koło straciło świeżość impulsów. Dopóki koło się
toczy (`wheel_valid`), zwolnienie pedału to ROLLING COAST — sesja zostaje TRZYMANA w

NIE nowy próg) jest zdarzeniem terminalnym → `COLD`. Wznowienie z tocznego coastu następuje WYŁĄCZNIE
przez prawdziwy forward (`confirm_edge || forward_pedaling`) — sam `rolling_valid` NIGDY nie daje
permission.

**Bez nowego enuma sesji, bez `assist_without_rotation` jako mechanizmu trzymania coastu, throttle i
pas_direction bez zmian.** **FLASH / COMMIT / PUSH = NO** — nic nie zostało wgranane ani zacommitowane.

## 1. Cel

Jedno pytanie, zadawane raz na tick: **czy rower naprawdę stoi?** FW-112.1 oddzieliło LIVENESS korbki
(fizyczna krawędź PAS) od PERMISSION (kierunek). FW-112.2 oddziela REAL_STOP od ROLLING COAST:

- po zwolnieniu pedału `real_stop` (liveness: brak krawędzi PAS przez timeout) odpala się natychmiast,
  nawet gdy rower jedzie bezwładnie — i dotąd natychmiast gasił sesję do `COLD`, wymuszając pełny zimny
  start przy następnym pedałowaniu;
- fizycznie jednak koło się toczy — kolarz tylko przestał naciskać. Zgłoszenie właściciela: przestaje
  pedałować na toczącym się rowerze → `COLD` → przy ponownym pedałowaniu pełny zimny próg zamiast
  natychmiastowego, tocznego wznowienia.

Rozwiązanie: REAL_STOP pozostaje zdarzeniem sesyjnym (żaden "ACTIVE na zawsze"), ale terminal sesji jest
**kwalifikowany** — `real_stop` kończy sesję dopiero, gdy koło też przestało się toczyć
(`!rolling_valid`). Coast to nadal zero permission: sesja siedzi w istniejącym `SUSPENDED_BY_DIRECTION`.

**Twardy zakres:** coast NIGDY nie daje permission (żaden rearm z samego `rolling_valid`), coast nigdy
nie generuje assist (zero Iq w finale przez `latched=false`), prawdziwy postój koła zawsze `COLD`
(conservative timeout), wznowienie tylko przez `confirm_edge || forward_pedaling` — dokładnie istniejąca
semantyka forward (z FW-112 v2), bez nowych ścieżek.

## 2. Audyt — dokładny mechanizm (przed zmianą)

| Cecha | Miejsce | Zachowanie |
|---|---|---|
| `real_stop` | main.c:2047–2283 (FW-112.1) | liczone z `pas_liveness`; werdykt "korbka bez krawędzi PAS przez timeout" |
| `terminal` sesji | ride_session.c | `non_direction_safety_cut \|\| assist_off \|\| real_stop` — `real_stop` bezwzględnie kończył sesję w KAŻDYM stanie (ACTIVE→COLD, SUSPENDED→COLD) w tym samym ticku |
| świeżość koła | main.c `speed_last_tick` + `SPEED_STOP_TICKS` | istniejący fakt: ostatni zaakceptowany impuls koła `SPEED_STOP_TICKS` (10600 ticków = 2.65 s @ 4 kHz) temu = koło toczy się ≥ ~3 km/h (2218 mm/impuls) |
| rearm SUSPENDED→ACTIVE | ride_session.c | `!direction_inhibit_active && (forward_confirmed_this_tick \|\| forward_pedaling)` → `fast_rearm_this_tick` (FW-112 v2; zero warunku obciążenia) |
| COLD→ACTIVE | ride_session.c | wyłącznie `!terminal && cold_start_ready` → `cold_arm_this_tick` (pełny zimny próg) |

**Luka:** `real_stop` w terminalu nie odróżniał "kolarz przestał naciskać, ale rower się toczy" od
"rower naprawdę stoi". Coast równał się COLD i wymuszał zimny start. Równocześnie samo dodanie
"rolling_valid jako alternatywnego permission" byłoby błędem (koło toczy się także przy cofaniu/wiezieniu).

**Decyzja właściciela (wybór 1):** bez nowego enuma — coast TRZYMA istniejący `SUSPENDED_BY_DIRECTION`;
kwalifikacja terminalu przez `rolling_valid`; rearm tylko prawdziwym forwardem.

## 3. Fix — kwalifikacja terminalu przez świeżość koła

Nowy moduł `src/ride_wheel.c` / `inc/ride_wheel.h`:
- `ride_wheel_valid(now_ticks, last_accepted_pulse_tick)` — **dokładnie ten sam fakt świeżości co main.c**
  (`(now - last) < SPEED_STOP_TICKS`), wyciągnięty do współdzielonej funkcji, żeby firmware i harness
  hostowy linkowały TĘ SAMĄ decyzję; odejmowanie unsigned przechodzi poprawnie przez wrap 32-bit.

`inc/rider_input.h`: nowe pole `bool wheel_valid;` (po `real_stop`).

`inc/ride_session.h`: nowe wejścia `rolling_valid` (kwalifikator terminalu) i `forward_pedaling` (czysty
forward zamiast `crank_direction_ok`, który wymagał też `fwd_run >= start_steps` — przy tocznym wznowieniu
`start_steps` nie jest jeszcze spełnione); docs terminalu zakwalifikowane.

`src/ride_session.c` (minimal-diff):
- `terminal = non_direction_safety_cut || assist_off || (real_stop && !rolling_valid)`;
- ACTIVE→SUSPENDED dodany warunek coastu: `direction_inhibit_active || (real_stop && rolling_valid)`
  (ACTIVE→COLD zostaje tylko dla terminalu);
- SUSPENDED→ACTIVE: `!direction_inhibit_active && (forward_confirmed_this_tick || forward_pedaling)` →
  `fast_rearm_this_tick` — **bez `rolling_valid` w warunku**; SUSPENDED→COLD dla terminalu bez zmian;
- COLD bez zmian (pełny zimny próg, `cold_arm_this_tick`).

Wpięcie:
- `src/main.c`: `#include "ride_wheel.h"`; w snapshotcie `rider_input` (jak main.c:2375):
  `.wheel_valid = ride_wheel_valid(control_now, speed_last_tick)`; w bloku FW-112-DIAG (`fd_in`)
  `.wheel_valid` i `.rolling_coast`;
- `src/ride_control.c`: session_in `.rolling_valid = rider->wheel_valid`,
  `.forward_pedaling = rider->crank_direction_ok` (komentarz wyjaśniający różnicę vs `pas_forward`).

Diagnostyka (`fw112_diag`, schema 1→2 — wymóg karty: odróżnić POWÓD zawieszenia):
- `FW112_FLAG_WHEEL_VALID 0x40`, `FW112_FLAG_ROLLING_COAST 0x80` (2 wolne bity bajta `reason_bits`, który
  jest pełny) + nowe pola wejściowe `wheel_valid`, `rolling_coast`;
- odczyt: trzymanie kierunkowe = `FW112_REASON_DIRECTION` + brak ROLLING_COAST; rolling coast =
  `ROLLING_COAST` bez powodu kierunkowego.

Świadomie nietknięte (minimal-diff): throttle, pas_direction, WAIT_FRESH_LOAD / TRACK_FAST / próg fresh
load, start_steps, torque FAST/RUN/filtry/kalibracja, assist_hold, progi zimnego startu, rampa hard-cut,
mapowanie mocy jazdy, boost, prąd silnika, FOC, Walk Assist / FW-113. `assist_without_rotation` NIE jest
mechanizmem trzymania coastu (coast generuje 0 Iq przez `latched=false`). Czas `SPEED_STOP_TICKS`
(2.65 s / ~3 km/h) NIE zmieniony — to istniejąca semantyka świeżości koła.

## 8. Finalne hardware evidence (HW acceptance)

Ostatni hardware test wykonano na **eVD 0.0366 (DIAG=1, M820 / BL820)**. Potwierdzono dwa różne,
wymagane kontrakty.

### A. ROLLING / COAST / DIRECTION SUSPEND — HW PASS

Potwierdzona ścieżka:

    ACTIVE
    -> reverse / coast / PAS loss
    -> SUSPENDED_BY_DIRECTION
    -> permission = 0
    -> no positive assist
    -> wheel context remains valid
    -> forward returns
    -> GRANTED
    -> RECOVERY_ENTER
    -> assist can return

Kluczowe: sesja NIE przechodzi fałszywie do `COLD` tylko dlatego, że PAS chwilowo zniknął podczas nadal
toczącego się roweru.

- **ROLLING REARM = HW PASS**
- **ROLLING COAST RETENTION = HW PASS**
- **REAL_STOP QUALIFICATION WHILE ROLLING = HW PASS**

Przykładowe sekwencje recordera (0.0366 DIAG=1), potwierdzone sprzętowo:

    REVOKED
    -> BLOCKED / SUSPENDED
    -> GRANTED
    -> RECOVERY_ENTER
    -> ZEROED / recovery continuation

oraz wielokrotne podobne cykle **bez false COLD**.

### B. TRUE PHYSICAL STOP — HW PASS

Oddzielny terminal-stop hardware test (log `log-2026-08-17-12-35-39-n0.log`):

    PAS stops
    -> wheel validity expires
    -> REAL_STOP
    -> COLD

Następny start po prawdziwym zatrzymaniu NIE używa rolling recovery — recorder pokazał:

    BLOCKED
    -> GRANTED
    -> COLD START

bez **RECOVERY_ENTER** (po prawdziwym stopie rolling rearm nie został użyty).

- **TRUE REAL STOP -> COLD = HW PASS**
- **COLD START AFTER TRUE STOP = HW PASS**

## 10. Finalna decyzja

FW-112 / FW-112.2 hardware acceptance is complete.

Rolling reverse, invalid-direction activity and no-pedal rolling coast no longer incorrectly collapse
the ride session into COLD while the bicycle is still moving.

Positive assist remains prohibited during reverse, invalid direction and coast.

Confirmed forward motion may restore rolling assist through the established rolling-rearm/recovery path.

A genuine vehicle stop still terminates the session conservatively into COLD, and the next start follows
the normal cold-start path.

**FW-112.2 — HARDWARE CLOSED**
